# Fleet device code → LLVM IR → gfx950 ISA

Compilation artifacts for the chiplet-scheduling and synchronization core of
[Fleet](https://arxiv.org/abs/2604.15379) (`../../fleet-chiplet-megakernel/`),
targeting **gfx950** (MI350 / CDNA4).

## What this is

**The real Fleet megakernel control flow**, compiled to gfx950:
`execute_worker()`, `execute_scheduler()`, and the three kernel entry points
(`worker_kernel`, `scheduler_kernel`, `persistent_kernel`).

`src/megakernel_loops.inc` is **`persistent_kernel.cuh` lines 180-1918,
sed-extracted verbatim** — `build.sh` re-extracts it on every run so it can
never drift from the source. Only the leaf compute kernels
(`_execute_task` / `_execute_gang_task`) are stubbed; those are CK-tile
GEMM/FMHA, not control flow.

| Content | Provenance |
|---|---|
| `src/megakernel_loops.inc` | **Verbatim** `persistent_kernel.cuh:180-1918`, regenerated by `build.sh` |
| `runtime_header.h`, `mpk_atoms.cuh`, `mirage/config.h` (via `-I`) | **Fleet sources, `#include`d unmodified** |
| `src/shim/` | **Hand-written.** Recreates the HIP environment (threadIdx, atomicAdd, `__shared__`, printf decl) on clang builtins. No Fleet code. |
| `src/megakernel.cpp` | Driver: build macros + stubbed leaf kernels |
| `src/fleet_probe*.cpp` | Isolated fragments (verbatim blocks, cited by `file:line`) for the fence audit |

**Not** Fleet's codegen output. `Graph::generate_task_graph()` emits
`permanent_output_dir/test.cu` — the whole Qwen3 model, prefill + decode.
That needs the full mirage build and is not here.

## Pipeline

Fleet has no IR of its own. Its "intermediate representation" is generated C++
source text:

```
Python task graph            mpk.gang_linear_layer(...)  → grid_dim=(8,1,1)
  └─ src/kernel/runtime.cc   emits C++ as strings        → test.cu + task_graph.json
       └─ hipcc / clang      → LLVM IR → AMDGPU backend  → gfx950 ISA → amdhsa ELF → .so
            └─ dlopen'd back into Python
```

The Chiplet-task abstraction exists only as `grid_dim=(8,1,1)` in Python, a
`uint16_t n_tile_count` field in a C struct, and an `if (is_gang_task_type(...))`
branch in the megakernel — never as IR.

## Build

```bash
./build.sh                      # defaults: clang 22.1.8, gfx950
CLANG=/path/to/clang ARCH=gfx942 ./build.sh
```

Needs **clang ≥ 19** for gfx950. Ubuntu's clang-14 has the `amdgcn` backend but
rejects the target ID.

## Results

### Megakernel control flow (from `out/megakernel.dis`)

| Kernel | instructions | branches | `s_sleep` | `buffer_wbl2` | atomics | LDS |
|---|--:|--:|--:|--:|--:|--:|
| `worker_kernel` | 1978 | 96 | 2 | 4 | 9 | 2000 B |
| `scheduler_kernel` | 4411 | 201 | 3 | 3 | 9 | 64 B |
| `persistent_kernel` (fused) | 6603 | 310 | 5 | 7 | 20 | 2072 B |

The persistent `while(true)` dispatch loop is visible as a backward branch
(`s_branch 65467` = −69) with `s_sleep 1` inside it — the queue-poll spin.
LDS budgets match the megakernel's own "must not exceed 3KB" constraint.

### Fence audit — zero coherence traffic on the hot paths

| Kernel | `buffer_wbl2` | atomic scope |
|---|---|---|
| `k_xcd_identity` — XCD discovery + leader election | 1 | agent cmpswap |
| `k_gang_broadcast` — scheduler → worker dispatch | **0** | plain |
| `k_gang_strip` — worker tile strip-mine | **0** | — |
| `k_two_level_signal` — Fig. 5 protocol | 1 *(branch-guarded)* | `sc0`, then `sc0 sc1` |
| `k_mmajor_traversal` — Fig. 3 index math | 0 | — |
| `k_poll_vs_depwait` — queue poll vs dep wait | 0 | 2× `buffer_inv` |
| `k_naive_signal` — Fleet's own non-XCD fallback | **1 *(unconditional)*** | `sc0 sc1` |

### The paper's claims, verbatim in the ISA

```asm
s_getreg_b32 s8, hwreg(HW_REG_XCC_ID, 0, 16)   ; §5.1 runtime XCD discovery
buffer_wbl2 sc1                                 ; §5.2 agent-scope release
global_store_dwordx2 v[2:3], v[0:1], off nt     ; §4.1 cache-streaming (nt)
global_store_dwordx2 v[0:1], v[2:3], off sc0 sc1; write-through, bypass L2
```

### The result that matters

Fleet's **naive fallback** (`persistent_kernel.cuh:1276-1284`):

```asm
buffer_wbl2 sc1                                      ; ← unconditional
flat_atomic_add_x2 v[0:1], v[2:3], v[0:1] sc0 sc1    ; ← every task pays
s_endpgm
```

Fleet's **two-level path** (`persistent_kernel.cuh:1226-1251`), disassembled
from `out/fleet_probe.o`:

```asm
s_cbranch_execz 19                                        ; skip if no tiles done
global_atomic_add_x2 v[0:1], v3, v[0:1], s[16:17] sc0     ; XCD-local: sc0, no fence
s_cbranch_execz 28                                        ; ← only last worker on XCD
buffer_wbl2 sc1                                           ;   the ONE writeback
flat_atomic_add_x2 v[0:1], v[2:3], v[0:1] sc0 sc1         ;   the ONE device atomic
```

Identical instructions, different control flow. The paper's 14.5× signal
reduction is a **compile-time property** — where `s_cbranch_execz` sits — not
something that needs an MI350 to observe.

Final object: `EM_AMDGPU`, `OS/ABI: AMDGPU - HSA`, `Flags: 0x54f, gfx950, xnack, sramecc`.

## Caveats

- Upstream LLVM 22 clang, not ROCm's fork. Same AMDGPU backend, so lowering is
  representative; instruction scheduling may differ.
- Never executed — no MI350 available. These are static compilation results.
